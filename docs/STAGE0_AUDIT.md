# Stage 0 — Stabilization & Technical Audit

Дата: 2026-10-22. Исходный коммит: `8eddc080af3e68d20e2b66c3d07d848bc9dae07c`.
Рабочая ветка: `chore/stage0-stabilization`.

## Объём и фактическая архитектура

Локальное приложение Python 3.11+; CLI `app.draft` / `app.bundle`, интерфейс `app.web` на `ThreadingHTTPServer`. Файловый кейс состоит из YAML-конфигурации, CSV-индексов, источников/переводов, extracted text, prompt/JSON, Markdown-разделов, DOCX и PDF. Юридическое содержание задаётся `workflows/`, `instructions/`, `schemas/`, `templates/`. LLM-provider — ручной; сетевых API для обработки кейсов нет.

Фактически поддержаны `eb1a_petition`, `o1b_petition`, `eb1a_rfe_response`, `eb2niw_petition`, `eb2niw_rfe_response`, `document_layout`. Модули `evidence`, `workflow`, `memo_builder`, `bundle_workflow`, `rfe_strategy`, `document_layout` разделяют основные операции; `pdf_assembly` собирает PDF с pikepdf и fallback на pypdf. На Stage 0 добавлены небольшие общие средства атомарной записи, блокировок и локальной HTTP-защиты; масштабного разделения модулей и изменения юридических шаблонов нет.

В начале работы были незакоммиченные пользовательские изменения в `app/memo_builder.py`, `app/rfe_strategy.py`, `app/web.py`, `tests/test_cli_smoke.py`, `tests/test_rfe_strategy.py` и отдельный launcher. Они сохранены и исключены из Stage 0-коммита. Проверяются как исходная рабочая копия с этими изменениями, так и независимое содержимое подготовленного коммита. Пользовательское расширение синхронизации структуры меморандума не является частью поставки Stage 0.

## Регрессионное покрытие и результаты

Исходный baseline в отдельном Python 3.12.10 venv с `.[pdf]`: **86 passed / 0 failed / 0 skipped**. Добавлены **37** Stage 0 regression/integration tests в отдельных тематических файлах. Один старый RFE fixture исправлен: минимальная строка с PDF header/EOF заменена настоящим одностраничным PDF, поскольку новая проверка правильно отклоняет прежний невалидный fixture.

Основные проверки:

```powershell
python -m pip install -e ".[pdf]"
python -m unittest discover -s tests -v
python scripts/check_full_suite.py
python -m compileall -q app tests
python -m pip check
git diff --check
git status --short
```

Финальный набор рабочей копии: **123 passed / 0 failed / 0 skipped**. Подготовленная независимая версия коммита: **121 passed / 0 failed / 0 skipped**; разница — два сохранённых незакоммиченных пользовательских теста. Установка и pip check успешны; compileall и diff whitespace check успешны. Exact versions проверенного Windows/Python 3.12 окружения записаны в `docs/STAGE0_DEPENDENCIES.txt`; диапазоны в pyproject не менялись. Результаты GitHub-hosted матрицы после push следует проверять отдельно: локальный успех не равен завершившемуся Actions run.

PDF-проверки фактически выполнялись: 4 теста `test_pdf_assembly.py`, новые EB-1A end-to-end и failure checks, long/image-only/corrupt PDF, существующие separator/layout/final-filing checks. Проверены original→translation порядок, число страниц, читаемость, предыдущий результат после неудачной пересборки, pypdf fallback и pikepdf.

Дополнительная ручная QA на синтетических данных Windows: Microsoft Word успешно преобразовал рабочий DOCX в **9 страниц**; evidence bundle содержит **5 страниц**, final filing — **14 страниц**. Poppler отрендерил все 14 страниц; визуально проверены заголовки, поля, переходы и нумерация, обрезаний/наложений не обнаружено. Poppler сообщил о fallback шрифтах Symbol/ArialUnicode; видимых дефектов в отрендеренных страницах нет. Неподготовленные разделы синтетического кейса содержат предусмотренные placeholders — это проверка pipeline, не готовая юридическая подача.

EB-1A: создание → Intake → originals/translations → scan/link → prompt → JSON import/validation → insert → DOCX → Exhibit Index → separator Markdown/PDF → final evidence PDF. O-1B: два repeatable units, разделение документов, импорт, memo и отсутствие дублей при пересборке; существующие тесты проверяют phases/Arts track/aliases. EB-1A RFE и EB-2 NIW RFE: существующие полноценные strategy/bootstrap/notice/initial-filing/new-evidence/unit-prompt/exhibit тесты сохранены и выполняются. EB-2 NIW petition и document_layout также остаются под регрессиями.

Реальные документы кейсов не использовались как fixtures и не изменялись. При проверке совместимости конфигураций читались только структура/типы путей без вывода значений; конфликтующих absolute/traversal workspace paths в доступных конфигурациях не найдено. Содержимое кейсов не передавалось внешним сервисам.

## Ограничения и решения следующего этапа

| Приоритет | Статус | Ограничение / следующий шаг |
| --- | --- | --- |
| P0 для публичного сервиса | `deferred` | Нет accounts, authorization, TLS, tenant isolation, sandbox обработки файлов, quota/rate limits, malware/resource isolation. Loopback/CSRF — только локальная граница. Public deployment до отдельного Server Readiness запрещён. |
| P1 storage | `deferred` | Атомарность обеспечивается на уровне отдельного файла; CSV+JSON+DOCX не являются единой транзакцией. Частично завершённые последовательности диагностируются и повторяются. Нет distributed/NFS locks и гарантий при power loss, аппаратной неисправности или одновременной ручной записи внешним редактором. Нужны backup/restore и transactional metadata перед multiuser. |
| P1 imports | `deferred` | Явный refresh mirror удаляет из импортированной копии отсутствующие в источнике файлы после успешного копирования. Нет retention/history для каждой импортированной версии. Ручные файлы следует хранить отдельно; источник не изменяется. |
| P1 extraction | `deferred` | OCR нет. Рисунки, диаграммы, OLE и сложная Word-разметка не гарантируют полный смысловой текст. Полные большие PDF/DOCX требуют памяти; серверу нужны отдельные workers и лимиты ресурсов. PDF preflight проверяет чтение страниц, не доказывает визуальную/юридическую корректность каждого потока. |
| P1 source identity | `deferred` | Автоматическое восстановление rename допускается только при однозначном checksum match в том же source kind. Дубликаты, изменение содержимого одновременно с переименованием и legacy locked rows без fingerprints требуют ручной проверки. |
| P1 local extensions | `needs_decision` | Незакоммиченные пользовательские расширения остаются отдельной работой. Их нельзя считать частью независимо поставленной версии; в частности, добавленная пользователем structure-sync функция имеет собственный backup/save путь. Для её выпуска нужен отдельный review/коммит и применение тех же правил безопасной записи. |
| P2 modules | `deferred` | Крупные web/workflow/memo/bundle модули, дубли template/path handling и широкие диагностические fallbacks сохраняются там, где нет подтверждённого дефекта. Следующий этап: отделить HTTP, case services, storage и conversion без изменения legal behavior, после характеризационных тестов. |
| P2 packaging | `deferred` | Используется полный source checkout + editable install. Самостоятельный wheel не поставляет все внешние template/workflow ресурсы. Нужны packaged resources и независимая миграция data root. |
| P2 templates/archives | `needs_decision` | В текущем tracked-дереве нет указанного предварительно DOCX ~37 MB; крупнейший шаблон около 1.62 MiB и используется Migrator variant. Крупных byte-identical дубликатов >1 KB нет. `templates/O1B/архив_не_использовать/`, O1A и отдельные reference templates — кандидаты на инвентаризацию, но отсутствие runtime-ссылки не доказывает отсутствие ручного использования. Ничего не удалено. Полная ручная privacy/rights review предоставленных legal templates перед публичным распространением остаётся ответственностью владельца; heuristic secret scan не является такой сертификацией. |
| P2 environment | `deferred` | Настоящие Office conversion и installed fonts проверены на данном Windows. Linux/другие версии Word требуют отдельной rendering QA; CI не устанавливает Office. |

Перед Google Drive экспериментом нужны явная модель прав доступа и происхождения документов, разделение originals/derived data, политика временных копий/удаления, metadata versions/checksums, credentials вне Git и тестовый sandbox с синтетическими материалами. Перед сервером дополнительно необходимы authentication/authorization, изоляция case storage, защищённые фоновые jobs, transactional state, мониторинг и проверяемое восстановление из резервных копий. Это рекомендации, не реализованные компоненты Stage 0.
